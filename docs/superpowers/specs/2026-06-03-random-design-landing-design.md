# Random Design MCP Landing Design

Date: 2026-06-03

## Goal

Build the initial frontend scaffold for a landing site that demonstrates the Random Design MCP server. The site shows multiple generated design variants for the same product pitch, so visitors can compare how Random Design changes visual direction while preserving content.

## Current Project State

The workspace is empty and is not yet a git repository. There are no existing project files, framework constraints, or visual conventions to preserve.

## Approved Stack

Use Vite, React, Tailwind CSS v4, and React Router.

Rationale:

- Vite gives a lightweight frontend scaffold with fast local iteration.
- React makes each generated design page an isolated component.
- Tailwind CSS v4 supports fast visual variation while still allowing custom CSS when a generated direction needs it.
- React Router gives each generated design a stable URL.

## Routes And Navigation

The site has a persistent top header with five links:

- Design 01: `/design-01`
- Design 02: `/design-02`
- Design 03: `/design-03`
- Design 04: `/design-04`
- Design 05: `/design-05`

The root route redirects to `/design-01`. The header remains available on every page so the user can compare variants quickly.

Future designs are added by inserting new route configuration entries and new page components. The structure must support adding Design 06 through Design 10 without changing the core app shell.

## Content Strategy

All five pages use the same product content. The product is Random Design MCP, described as a Model Context Protocol server that generates frontend design directions for landing pages, interfaces, and experiments.

The copy should read like a promotional landing page for developers, designers, and AI tool builders. Keeping the content identical across pages is intentional: the project compares generated design direction, not different narratives.

The initial shared content should include:

- Product name: Random Design MCP
- Hero claim: generate distinct frontend design directions on demand
- Short explanation of what the MCP server returns
- Three to four product benefits
- A section showing how a prompt becomes a design direction
- A clear call to action, such as inspecting the prompts or generating the next batch

## Generated Design Data

Each design page is backed by structured data:

- `slug`: stable route slug
- `navLabel`: visible header label
- `generationPrompt`: full Markdown prompt returned by Random Design MCP
- `summary`: short label derived from the MCP output for internal/reference use
- `component`: React component that renders the page

The five initial prompts are generated by the Random Design MCP server in compatible mode. They are not manually selected aesthetic themes.

## Prompt Block

Every page ends with the same service-style prompt block. This block is visually consistent across all designs and shows the full `generationPrompt` for the current page.

The prompt block is intentionally not restyled per design. It is metadata, not part of the generated landing page. This keeps prompts readable and makes comparison easier.

## Component Boundaries

Use these core boundaries:

- `App`: router and app-level layout.
- `Header`: shared navigation.
- `PromptBlock`: shared prompt display.
- `designs` config module: route metadata and prompt text.
- `SharedLandingContent`: reusable copy/data for all pages.
- `Design01Page` through `Design05Page`: distinct visual implementations using the shared content.

The design page components may have different markup when needed for their layout, but they should consume the same shared content source.

## Styling Rules

Tailwind utilities are the primary styling mechanism. Custom CSS is allowed for:

- generated visual effects
- page-specific animations
- texture overlays
- responsive details that are clearer in CSS than inline utility chains

Avoid making the whole site look like one theme. Each design page should feel generated from its own prompt, while the header and prompt block stay stable enough for navigation and comparison.

## Accessibility And Responsiveness

Each page must:

- preserve readable contrast
- keep real button/link labels clear
- avoid text overlap on mobile and desktop
- support keyboard navigation through the header links
- render cleanly at common mobile and desktop widths

## Testing And Verification

After implementation:

- run the build command
- run local dev server
- inspect all five routes in browser
- verify the prompt block appears on every page
- verify navigation works across all five pages
- check mobile and desktop layouts for obvious overlap or unreadable text
